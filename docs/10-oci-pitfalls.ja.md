# 10 OCI 困った集：AWS／Azure／GCP 経験者が初めての OCI で詰まる所

[English](10-oci-pitfalls.md) | 日本語

OCI を初めて構築する過程で、実際に詰まった所・調査で判明した所・事前に注意すべき所を貯めていく記録。[09 の設計](09-oci-cloud-dev-environment.ja.md)に基づく構築の進行に合わせて追記する。

各項目のステータスは3種類。**実体験**＝この構築で実際に当たった。**調査で判明**＝ドキュメントや公式情報の確認で分かった。**注意**＝未遭遇だが、当たりそうなので先に書いておく。

## No.1 サインインの入口が「テナンシー名」

**状況**：cloud.oracle.com を開くと、ユーザー名とパスワードの前に「Cloud Account Name」（テナンシー名）を聞かれる。1Password の自動入力ではこの欄がうまく埋まらず、ページが遷移しないと入力が消えてしまった。テナンシー名を知らないと、最初の画面から先へ進めない。

**対処**：テナンシー名は、OCI 登録時に届いたウェルカムメールに書いてある。サインインできた後は、コンソール右上のプロフィールメニューでも確認できる。教訓として、テナンシー名はパスワードマネージャのメモ欄に残しておく。

**他クラウドだと**：AWS はメールアドレス／IAM ユーザー、Azure は Microsoft アカウント、GCP は Google アカウントから入る。「アカウント自体の名前を先に聞かれる」入口は OCI 独特で、ここが最初の壁になる。

## No.2 無料 A1 枠は 2026-06-15 に半減していた

**状況**：解説記事やブログの多くは今も「Ampere A1 は 4 OCPU／24GB が無料」と書いている。しかし Oracle 公式の Always Free ドキュメントでは、無料テナンシーの枠は月 1,500 OCPU 時間＋9,000 GB 時間で、常時起動に換算すると約 2 OCPU／12GB に半減している（2026-06-15 の変更、大きな告知はなし）。4 OCPU／24GB は、PAYG テナンシーが枠内で使える数字になった。

**対処**：無料枠の数字は記事ではなく現行の公式ドキュメントで確認する。記事を参照するときは公開日を見る。[09 の設計](09-oci-cloud-dev-environment.ja.md)も 2 OCPU／12GB を上限として組んである。

**他クラウドだと**：無料枠の条件変更自体は各社にある。本件が厄介なのは、告知が目立たないまま数字だけが半分になり、古い記事との差に気づきにくい点である。

## No.3 東京リージョンの A1 容量不足

**状況**：2026-11-01、09 の設計通り（VM.Standard.A1.Flex、2 OCPU／12GB、アベイラビリティドメイン AP-TOKYO-1-AD-1、Ubuntu 24.04 ARM）でインスタンス作成を試みたところ、"Out of capacity for shape VM.Standard.A1.Flex in availability domain AD-1" というエラーで失敗した。東京はアベイラビリティドメインが1つしかないため、「別の AD を試す」という手も使えない。

**対処**：判断として、大阪リージョンで作ることにした。東京はエンタープライズ利用が多く、A1 の空きが出る見込みは薄い。大阪は DR の逃がし先としてよく使われるリージョンで、開発箱であれば多少の遅延は許容できる。東京に作成済みの VCN／サブネット／インターネットゲートウェイは、無料で無害なため残置した（将来東京で再挑戦する際に再利用できる）。

**他クラウドだと**：AWS でも人気のインスタンスタイプが AZ 単位で枯れることはある。ただし無料枠のシェイプで枯渇が常態化している点は、OCI の無料利用ならではの詰まりどころである。

## No.4 GUI の言葉が他社とずれる

**状況**：コンパートメント、VCN、セキュリティリスト、アベイラビリティドメイン、シェイプ、アイデンティティドメイン。概念自体は他クラウドにもあるが、名前と階層の切り方がずれており、初見では「何を触ればいいか」が画面から読み取れない。

**対処**：下の対応表を手元に置く。特に、コンパートメントは「アカウント／サブスクリプション／リソースグループの役割をまたぐ仕切り」、アイデンティティドメインは「サインイン経路そのものを分ける IAM の層」と押さえると迷いにくい。

| OCI | AWS | Azure | GCP |
|---|---|---|---|
| コンパートメント | ≒ アカウント／OU 的な仕切り | ≒ サブスクリプション／リソースグループ | ≒ プロジェクト／フォルダ |
| VCN | VPC | VNet | VPC |
| セキュリティリスト／NSG | セキュリティグループ | NSG | ファイアウォールルール |
| アベイラビリティドメイン | アベイラビリティゾーン（AZ） | 可用性ゾーン | ゾーン |
| シェイプ | インスタンスタイプ | VM サイズ | マシンタイプ |
| アイデンティティドメイン | ≒ IAM の認証基盤 | ≒ Entra テナント | ≒ Cloud Identity／組織 |

**他クラウドだと**：独自用語自体は各社にある。OCI は特に「リソースの仕切り」と「ネットワークのファイアウォールが2層（セキュリティリストと NSG）」の対応が取りにくく、用語で詰まる比率が高い。

## No.5 アイドルな無料インスタンスは回収され得る

**状況**：Always Free のコンピュートには、アイドル状態が続くインスタンスを Oracle が回収するポリシーがある。正確な閾値（どの程度の低使用で対象になるか）は要確認。

**対処**：対策は、箱を「置いてあるだけ」にしないこと。[09 の設計](09-oci-cloud-dev-environment.ja.md) Phase 5 で実際の開発作業を移し、日常的に使う開発箱にする。閾値の裏が取れたらこの項目を更新する。

**他クラウドだと**：無料枠は「期限」や「上限」で管理されることが多く、使われ方を見て回収される、という運用は他社の感覚では意識しにくい。

## No.6 FIDO セキュリティキーだけだとリモート／エージェントのブラウザから入れない

**状況**：2026-11-01、OCI のサインインで2段階認証を求められたが、登録済みの方法が FIDO セキュリティキーだった。キーはユーザーのローカルマシンにあり、WebAuthn はブラウザが動いているマシン側のキーにしか届かないため、リモート環境のブラウザからは認証を完了できず、サインイン自体ができなかった。ついでに、古い Oracle ドキュメントが案内する「マイ・プロファイル」というメニュー項目は、現行のコンソールには存在しない点でも迷った。

**対処**：認証アプリ（TOTP）を追加の方法として登録した。経路は、プロフィールメニュー →「User settings」→ Security タブ → 2段階認証 → Mobile app → Configure。キーは 1Password に登録し、TOTP をデフォルトの方法に設定した。FIDO キーはバックアップとして残してある。教訓として、エージェントやリモートのブラウザからサインインさせる前提なら、持ち運べる TOTP を事前に登録しておく必要がある。

**他クラウドだと**：セキュリティキーがローカルマシンに縛られるのは AWS／Azure／GCP でも同じで、WebAuthn の仕様上どこでも起きる。OCI 固有なのは、対処の場所が古いドキュメントの言う「マイ・プロファイル」ではなく「User settings → Security」である点だけである。

## No.7 無料テナンシーはホームリージョンしか購読できない

**状況**：2026-11-01、東京の A1 容量不足（No.3）を受けて大阪（Japan Central）を購読しようとしたところ、Region Management に "You have exceeded the maximum number of regions allowed for your tenancy" と表示され、大阪に限らず未購読の全リージョンで Subscribe が無効化されていた。無料テナンシーのリージョン購読はホームリージョン（ここでは東京）1つまでで、逃がし先のリージョン自体を開けない。

**対処**：テナンシーを PAYG にアップグレードするとリージョン上限が外れ、大阪を通常通り購読できた。第2リージョン（容量不足時の逃がし先や DR）を前提にする設計なら、最初から PAYG 化を見込むか、「ホームリージョンのみ」を無料テナンシーの制約として織り込む。なお、アップグレード自体も先に別の壁に当たった（No.8）。

**他クラウドだと**：AWS は通常リージョンがアカウントで一通り有効であり、Azure／GCP のサブスクリプションも単一のホームリージョンに縛られない。リージョン「購読」の上限が1というのは、OCI の無料利用ならではの癖である。

## No.8 Promo／Free Trial テナンシーには支払い方法が未登録で、PAYG アップグレードが進まない

**状況**：2026-11-01、「Upgrade and Manage Payment」ページで Payment Method が「-」表示のままで、「Upgrade your account」ボタンが無効化され、"Add a payment method to upgrade a subscription plan." と警告が出た。このテナンシーは Promo／Free Trial として作成されており、カードが一度も登録されていなかった。09 の設計（Phase 0 でカード登録済みを前提）との食い違いである。

**対処**：カード追加は所有者本人が行う。Upgrade and Manage Payment ページで Payment Method 行の「・・・」アクションメニューを開き、Add Payment Method から登録する。支払い情報の入力は、リモートブラウザで作業するエージェントにはできない（すべきでない）手順である。カードが登録されるとアップグレードボタンが有効になり、PAYG 化が通った。

**他クラウドだと**：有料化に支払い方法が要るのはどこも同じだが、本件の罠は「カードなしで始まったトライアルは、テナンシー側に何も残っていない」点にある。ボタンが押せない理由は、Payment Method 行を見るまで分からない。

## No.9 大阪では通常の Ubuntu 24.04 イメージが x86 専用で、Arm 版 24.04 は Minimal のみ

**状況**：2026-11-01、大阪（Japan Central）で VM.Standard.A1.Flex のインスタンスを作る際、イメージ一覧の通常の「Canonical Ubuntu 24.04」が x86_64 版で、Arm シェイプと互換がなかった。A1.Flex で使える Ubuntu 24.04 は「Canonical Ubuntu 24.04 Minimal」（aarch64）だけだった。

**対処**：Minimal の aarch64 イメージを使い、不足するパッケージはベースセットアップ時に追加する（Minimal は通常版に入っているものの一部を省いている）。Arm シェイプ用にイメージを選ぶときは、名前とバージョンだけでなくアーキテクチャを確認する。Arm 版の有無はリージョンによっても変わる。

**他クラウドだと**：AWS の AMI もアーキテクチャ別に公開されるが、EC2 コンソールは選択したインスタンスタイプで絞り込んでくれる。OCI の作成フローは非互換な組み合わせでも先へ進めてしまうため、アーキテクチャの確認がこちらの仕事になる。

## No.10 Usage API はホームリージョン必須で、DAILY 粒度は日の境界が要る

**状況**：2026-11-01、midorun（大阪）上のコストガードスクリプトが Usage API で月初来の利用額を読もうとしたところ、インスタンスのリージョン宛ての呼び出しは 403 "Please go to your home region" で失敗した。ホームリージョン（東京）へ向け直すと、今度は別の失敗が出た。granularity が DAILY の場合、終了時刻が日の境界（00:00 UTC）ちょうどでないと 400 InvalidParameter になる。スクリプトが通知を送る Notifications トピックもホームリージョンにあり、一方で Compute の呼び出しはインスタンスのリージョン（大阪）宛てである。

**対処**：リージョンをまたぐガードスクリプトでは、クライアントごとにリージョンを持たせる。Usage API と Notifications はホームリージョン、Compute はインスタンスのリージョン。DAILY 粒度では終了時刻を翌日の境界（00:00 UTC）に合わせる。予算・課金系の API はホームリージョンのサービスだと最初から想定しておくと、403 の理由探しで止まらない。

**他クラウドだと**：AWS の Cost Explorer も us-east-1 に寄せるホームリージョン型のエンドポイントで、この型自体は OCI 固有ではない。DAILY 粒度で日の境界を要求される点が、当たらないと分からない部分である。

## No.11 Muse の作業環境からの外向き SSH はデフォルトで無効

**状況**：2026-11-01、09 の構築はフワッチ（Muse）がクラウドからクラウドへ実行する担当だったが、Phase 2〜4 で必要になるインスタンスへの SSH が、作業環境側のデフォルト設定で拒否された。外向き SSH は初期状態ではオフであり、インスタンスが稼働済みの段階でセットアップが止まった。

**対処**：ユーザーが Muse の設定（Permissions → Direct network protocols）で ssh を Deny から Ask に変更すると、接続ごとに承認プロンプトが出て通るようになった。教訓として、エージェント主導の構築では、クラウド側の確認と並べて作業環境側の外向き権限（SSH を含む）を Phase 0 で確認しておく。

**他クラウドだと**：これは OCI の話ではなく、作業者側ツールの壁である。エージェントが構築を担う構成ではどのクラウドでも起こり得る依存であり、「クラウド側が整えば経路もあるはず」という思い込みが罠になる。

## No.12 公開 SSH を閉じる前に、作業者側のアクセス経路を確認する

**状況**：2026-11-01、09 の設計 §5 は「Tailscale が入ったら公開 SSH を閉じる」だった。箱は tailnet に `midorun`（100.75.1.65）として参加したが、フワッチの作業環境からその CGNAT アドレスへの SSH はネットワークレベルで拒否された（"Operation not permitted"）。公開 IP への SSH は問題なく通る。予定どおり公開側を閉じていたら、構築した作業者自身が箱から締め出されるところだった。

**対処**：インバウンドを締める前に、置き換え先の経路を所有者の端末だけでなく、アクセスが必要な全作業者から試す。今回は所有者の判断で、公開ポート 22 は鍵認証のみ（実機で確認：PasswordAuthentication no、PubkeyAuthentication yes、PermitRootLogin without-password）で当面開けたままにし、作業環境側の tailnet 経路が通るようになったら再検討することにした。

**他クラウドだと**：「公開ポートを閉じてメッシュ VPN に寄せる」という堅牢化を自動化が担う構成なら、どこでも同じ罠がある。メッシュ経路は人間には通っても、作業しているエージェントには通らないことがある。ルールを変える前に、作業者ごとの到達性を確認する。
